# Floci (AWS) findings

Behaviour found while driving `floci/floci:2.3.0` with Terraform (`hashicorp/aws` 6.71.0) and
boto3 from the toolbox container (`CLOUD=aws`). Each entry: what happens, how it was verified,
and what the lab does about it. Re-test gated resources with `-var include_known_emulator_gaps=true`.

| ID | Area | Finding | Lab workaround |
|---|---|---|---|
| A-01 | Auth / upgrade | Floci 2.x seeds a different deployer: access key **`floci`** / secret `floci` (user `floci-deployer`, from the startup log). The 1.x key `fake-agent-key-001` — hard-coded in `aws/conftest.py` — is now rejected (`InvalidClientTokenId`), so the 1.x pytest harness breaks on upgrade. | Lab toolbox signs as `floci`/`floci`. |
| A-02 | Auth / security | With `FLOCI_SERVICES_IAM_ENFORCEMENT_ENABLED` and `FLOCI_AUTH_VALIDATE_SIGNATURES` on, the well-known default **`test`/`test` is accepted as the account root** (`arn:aws:iam::000000000000:root`). Any client that never set credentials gets root, so IAM policy enforcement cannot be tested against default-credential callers. | Lab never uses `test`; probe in `tests/probe_identity.py`. |
| A-03 | Web UI | Console at `http://localhost:4566/_floci/ui` answers (200); 127 services listed in `/_floci/health` (1.5.15 had 46). | — |
| A-04 | EC2 | The instance does not keep its `launch_template`, and the **root volume reads back unencrypted** although Terraform requested KMS encryption — a test would see weaker security than the code asks for; both would replace the instance on every plan. | `ignore_changes = [launch_template, root_block_device]`. |
| A-05 | ElastiCache | Replication group drops `security_group_ids`. | `ignore_changes`. |
| A-06 | Tags | Backup plan and EC2 key pair drop their tags (`default_tags`). | `ignore_changes = [tags, tags_all]`. |
| A-07 | S3 Control | Provider 6.x reads bucket tags through S3 Control, which prefixes the account to the host (`000000000000.floci-lab`). Not a Floci bug, but labs need `*.<floci host>` to resolve to the emulator. | Toolbox guard maps `*.floci-lab` to Floci. |
| A-08 | S3 encryption | The bucket's default encryption (`aws:kms` + bucket key) is stored and `GetBucketEncryption` returns it, but **objects put without an SSE header come back unencrypted** (`HeadObject` has no `ServerSideEncryption`). An explicit `ServerSideEncryption=aws:kms` header works. A test of "bucket default encryption applies" would pass on real AWS and fail here, or the reverse for a test that expects the header. | Smoke reports GAP. |
| A-09 | ElastiCache | Floci fronts the Valkey container on `floci-lab:6379` and **enforces IAM auth** (anonymous → `NOAUTH`; a SigV4-presigned `connect` token for user `default` → `PONG`; static passwords rejected). But it serves **plaintext only** although the group reports `transit_encryption_enabled = true`: a TLS client fails the handshake. | Smoke authenticates with an IAM token; TLS → GAP. |
| A-10 | API Gateway v2 | `api_endpoint` is the real-AWS host `https://<id>.execute-api.us-east-1.amazonaws.com`, which the egress guard sinks (and which would leak without it). Floci serves the same API at `http://floci-lab:4566/_aws/execute-api/<id>/<stage>/<path>` (also `/restapis/<id>/<stage>/_user_request_/…`, or port 4566 with the real `Host` header). The **first call blocks ~18 s and more** while Floci pulls `public.ecr.aws/lambda/python:3.12`; a 30 s client timeout fails on a fresh machine. | Smoke uses the `/_aws/execute-api` path with a 120 s timeout. |
| A-11 | RDS | The DB endpoint is the **Floci container's IP and a proxied port** (`172.22.0.2:7001`), not an RDS hostname on 5432. Clients must read `Endpoint.Address`/`Port`; hard-coded `:5432` fails. PostgreSQL 16.15 answers with the Secrets Manager password. | Smoke reads the endpoint from `DescribeDBInstances`. |
| A-12 | ECR push | The repository URL is `<account>.dkr.ecr.<region>.localhost:4566/...` and Floci routes registry calls by that `Host` header (plain `localhost:4566/v2/` → 404). **Docker Desktop's daemon cannot resolve `*.localhost`**, so `docker login`/`docker push` with the real URL fail (`no such host`). | `scripts/ecr-push.sh`: crane on the lab network with the ECR name mapped to Floci, logged in with a real `GetAuthorizationToken` password. |
| A-13 | ECR / security | **The registry accepts anonymous push and pull** (no `docker login`) while IAM enforcement is on: a test that "only authorised principals can push" passes here and would fail on AWS. Tag immutability *is* enforced (`TAG_INVALID` on re-push of `0.2.0`). `scan_on_push = true` is stored but no scan runs (`imageScanStatus` empty). | Recorded; the lab still logs in with a token. |
| A-14 | EKS / security | The cluster says `endpointPublicAccess = false`, yet the API is **published on the host at `0.0.0.0:6500`** and the reported endpoint is `https://localhost:6500` (unusable from other containers; the cert names only `localhost`). | kubeconfig targets `floci-aws-eks-<cluster>:6443` with `tls-server-name: localhost`. |
| A-15 | EKS auth | In `CONFIG_MAP` mode (the provider default) Floci creates no `aws-auth` ConfigMap and its token webhook ignores one if you add it: **no IAM identity can log in**. The webhook reads only access entries. | `access_config { authentication_mode = "API" }`. |
| A-16 | EKS API | **`UpdateClusterConfig` is not implemented** (HTTP 400 with a non-JSON body), so the auth mode cannot change in place; the cluster had to be replaced. Floci also **deleted the cluster while node group `default` was still attached** and kept the node group; AWS refuses that delete. | Auth mode set at creation. |
| A-17 | EKS auth | `bootstrap_cluster_creator_admin_permissions = true` creates **no access entry** for the creator. | Explicit `aws_eks_access_entry` for the deployer. |
| A-18 | EKS API | **`AssociateAccessPolicy` is not implemented** (HTTP 400, non-JSON), so `AmazonEKSClusterAdminPolicy` cannot be attached to an access entry. | Association gated behind `include_known_emulator_gaps`. |
| A-19 | Auth (root cause for EKS) | With `FLOCI_AUTH_VALIDATE_SIGNATURES` on, **presigned (query-string SigV4) URLs are rejected for Query-protocol services**: STS `GetCallerIdentity` and SQS → `SignatureDoesNotMatch`, while S3 presigned GETs work. Every EKS token (`aws eks get-token` or our own) is a presigned STS call, so the token webhook returns `authenticated: false` for all of them. Also: EKS Pod Identity injection is off unless `FLOCI_TLS_ENABLED=true` (startup warning). | `scripts/eks-deploy.sh` applies with the k3s admin kubeconfig (bypasses EKS IAM auth; noted). `scripts/eks_kubeconfig.py` keeps the real IAM path for when Floci fixes it. |
| A-20 | Restarts / RDS | After a Floci restart the DB endpoint moved from `172.22.0.2:7001` to `10.50.0.2:7001` (a refresh reports `address`/`endpoint` changed) and connections to the new address time out. Anything holding the old endpoint breaks; smoke `rds postgres` fails. | Recorded. The SaaS reports it as `observed` drift (endpoint kept, check consumers). |
| A-21 | Restarts / EKS | After a restart `DescribeCluster` says `ACTIVE`, but the k3s container exits: `failed to find interface with specified node ip` (Docker gave it a new address, like Azure F-31). The control plane reports a healthy cluster with no Kubernetes behind it. The EC2 instance also stays `pending`. | Recorded; only the smoke test (`eks + ec2`) sees it. |
| A-22 | SQS import | `terraform import` / an import block with Floci's queue URL (`http://floci-lab:4566/000000000000/<name>`) fails: `could not parse ... as SQS URL`. The AWS form (`https://sqs.us-east-1.amazonaws.com/000000000000/<name>`) works through the endpoint override. | Import with the AWS URL form. |
| A-23 | EC2 state | After a restart `DescribeInstances` says `pending` with no reason while the instance container runs. `StopInstances` reports `stopped` but leaves the container running; after the container is stopped by hand, `StartInstances` reports `running` without starting it. API state and container are out of step both ways. | `scripts/recover-after-restart.py` stops and starts through the API and keeps the container in line. |
| A-24 | RDS restore | **`RestoreDBInstanceToPointInTime` copies the source's current data**, not the data at `RestoreTime`. A row deleted 2 s after the restore time was missing on the restored instance. Snapshot restore is correct. Both restore calls apply AWS's defaults (subnet group `default`, the default VPC security group, `PubliclyAccessible: true`), just as AWS does. | PITR is drilled on real AWS only; `state/README.md` T5. |

## Containers: ECR → EKS

`scripts/ecr-push.sh` copies `ghcr.io/kmn1625/hello-api` 0.2.0 into the lab ECR (digest unchanged,
`sha256:06a03e37…`); `scripts/eks-deploy.sh` applies `k8s/hello-api/overlays/eks`. The k3s node mirrors the
ECR hostname to Floci, so the pods pull the real repository URL by digest (6.7 s). Verified: 2/2 pods Running,
`GET /` → `{"env":"eks","version":"0.2.0"}`; restricted Pod Security rejects a privileged pod; default-deny
NetworkPolicy blocks a client in another namespace.
